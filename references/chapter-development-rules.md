# 章节增量完善规则

## 1. 开发单元

以一个 `chapter_code` 为验收单元，以 `section_role` 为共性规则单元。规则按以下顺序叠加：

`全局红线 → 章节类型规则 → 具体章节覆盖 → 项目章节任务包`

全局红线不得被后续层覆盖。共性规则只放在章节类型层；章节覆盖只记录真正不同的组装、完成和校验要求。

## 2. 单章闭环

1. 从 `assets/chapter-rule-workbench-template/CHxx-章节问题卡.md` 建立脱敏问题卡。
2. 只读取当前章节相关的蓝图、生成器、验证器、测试和脱敏样例。
3. 使用 `--chapter` 重建章节计划并导出单章任务包。
4. 只生成当前章节，执行章节校验并检查问题卡中的验收项。
5. 校验失败时只修改当前章节规则或明确共享依赖，不重新生成全文。
6. 章节通过后单独提交，记录受影响的章节族。

客户原始文档、公司标准方案和项目数据库不得进入公开Skill仓库；测试只使用合成或脱敏材料。

## 3. 回归分级

- `chapter`：每次修改后运行，只覆盖当前章节契约和直接生成链。
- `family`：章节通过后运行，覆盖同一 `section_role` 的关联章节。
- `full`：修改全局红线、公共数据库结构、公共组装器或准备发布时运行。

使用 `run_chapter_regression.py` 执行分级回归。测试失败时保存首个有效错误摘要，不把完整冗余日志反复送入模型上下文。

## 4. 5.1.1首个验收契约

`5.1.1 业务应用系统建设`以客户清单为外边界。确认能力映射后，能力绑定的全部受审标准方案块必须按原顺序进入工作稿；只允许清理禁用词和调整项目语态，不得排序、摘要、截断或反向扩大客户范围。工作稿保留不可见的语料块追踪标记，Word交付时统一过滤。

本章至少检查：确认范围承载率、动态目录完整度、标准方案块标记覆盖率、标准方案正文覆盖率、禁用词和编制过程提示语。

## 5. 2.1.2信息化建设现状验收契约

`2.1.2 信息化建设现状`只把已确认或材料明确的医院事实写成确定性现状。评级目标、当前评级、参评状态、医院发展背景和调研事实必须分开绑定：

- `acceptance.*`只代表规划或验收目标，不得改写为当前已达到等级；
- 当前评级必须来自`current_state.assessment.*`或等价的已绑定现状事实；
- “未参评”表示没有正式外部评级结果，不得换算为零级或推导为不具备相应能力；
- 目标高于当前等级时，只能形成“需按目标评价版本开展差距核查”的分析结论；具体功能、数据、流程或管理缺口仍须由调研记录、正式测评结果或医院确认支持；
- 创三甲、医院发展规划等属于业务背景和约束，可用于确定调研重点，不得直接证明某项信息化能力缺失；政策和评价标准只能提供解释框架，不能证明医院现状；
- 客户建设清单仅可作为现状调研对象和拟建边界，不能写成医院已经部署、已经使用或已经通过验收的事实。

本章至少检查：确定性现状事实来源覆盖率、目标与当前状态隔离、未参评语义、拟建清单冒充现状、冲突和未知披露、应用系统、数据接口、基础环境、安全和运维维度完整性。

## 6. 全量回归触发条件

出现下列任一变化时，不得只运行章节测试：

- 修改全局事实、范围、政策或交付红线；
- 修改数据库迁移、目录签名、草稿采纳或全文组装；
- 修改两个以上章节类型共用的生成逻辑；
- 准备发布或推送稳定版本。
