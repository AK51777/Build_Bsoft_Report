# 政策证据、四类编制依据和政策背景生成规则

## 1. 证据链

执行：`部门目录/项目线索 → 项目画像 → 官方检索 → 原文核验 → 条款提取 → 适用性匹配 → 用户确认 → 排序 → 编制依据 → 政策背景`。

搜索摘要、自媒体转载、聚合网站和模型记忆只能用于发现候选，不能作为最终政策证据。最终证据必须是官方网页、官方PDF、正式数据库或用户提供的正式原文，并保存URL、核验日期和必要原文。

当前部署使用数据库 `hrr_feedback`、登录账号 `hrr_feedback`、schema `medical_report_kb`，密码只从环境变量读取，不写入Skill或项目文件。部门整理的政策目录存入 `medical_report_kb.policy_catalog` / `medical_report_kb.policy_catalog_entry`；`medical_report_reader` 若存在只是可选只读角色名，不是数据表，也不是当前部署账号。目录项可以包含政策、标准、评价指南或项目文件，但它本身只是一份候选清单；只有建立对应 `policy_document`、完成官方核验、切分并发布 `policy_clause` 后，才能进入项目正式政策快照和报告依据。

部门目录的原始索引号不是数据库唯一键。索引号重复时必须保留全部来源行，记录出现次序并标记 `index_conflict`；不得静默覆盖、合并或丢弃。候选匹配按来源行稳定排序，标题级候选统一标记为 `structure_only` 和 `candidate_only`。

## 1.1 原文采集暂存与正式证据隔离

目录发布后可用 `capture_policy_sources_postgres.py` 对全部活动目录项建立原文采集状态。首次调用必须先运行 dry-run；生产写入必须同时给出 `--apply` 和与目标数据库精确一致的 `--confirm-database`。采集器默认不继承系统代理，确需使用受控代理时显式指定 `--use-system-proxy`；原始 HTML、PDF 或附件应保存到仓库外私有归档目录，并在数据库保存最终URL、HTTP状态、内容类型、原始哈希、提取文本及哈希、附件URL、身份匹配结果、抓取错误和核验状态。

`policy_source_capture` 是全量、可恢复、未核验的暂存层，允许保存缺链接、非法链接、HTTP 403/404/410/412、网络失败、超限文件、二进制待提取和正文身份不匹配等状态。草案、征求意见稿、内部材料、专家共识和会议谈话必须标为 `draft_or_internal` 或 `reference_only`。任何采集结果默认均为 `unverified/pending`；`review_policy_source_capture_latest` 只供补链、重试和人工核验，不属于 `runtime_*` 正式证据视图，也不得直接生成编制依据或政策背景。

完成正文采集后仍须逐文件核对正式名称、文号、发布机关、发布日期、最终官方URL、效力和替代关系，再切分必要条款，填写审慎摘要、用途许可、禁用主张、主题和适用对象。只有经受控复核生成的 payload 才可交给 `import_verified_policies_postgres.py --publish`；禁止把采集文本整篇自动切一条、批量标记为 `verified` 或直接复制为 `policy_document` / `policy_clause`。

采集完成后先运行 `build_policy_source_review_workpack.py`，从指定目录的最新采集视图只读生成 JSON、CSV 和 Markdown 复核工作包。工作包输入签名必须覆盖目录内容哈希以及每条记录的目录行哈希、采集ID、最终URL、抓取状态、内容就绪状态、身份状态、原文哈希、提取文本哈希和当前审核状态；任一项变化即生成新的复核运行ID，旧工作包不得继续回写。

复核队列使用固定优先级：身份完全匹配文本 → 部分匹配 → 身份不一致 → 无法自动判断 → 二进制提取 → URL重校验 → 网络重试 → 人工补源 → 其他采集重试 → 未采集 → 非正式资料排除 → 非活动目录排除 → 已有人工状态复查。`draft_or_internal`、`reference_only` 和非活动目录项必须优先进入排除队列，不得因已经抓到正文而升级为正式候选。所有导出行的 `formal_publish_eligible` 固定为 `false`，人工模板的 `verification_status` 固定为 `unverified` 且条款列表为空；该脚本不得生成 `import_verified_policies_postgres.py` 可直接发布的载荷。

```text
MEDICAL_FEASIBILITY_DB_PASSWORD=<password> python scripts/build_policy_source_review_workpack.py --catalog-id <catalog-id> --output-json <review.json> [--output-csv <review.csv>] [--output-md <review.md>] --host 127.0.0.1 --port <tunnel-port> --database <database> --user <user>
```

默认工作包只保存提取文本长度、哈希和有界预览；仅在受控私有目录人工复核时显式使用 `--include-extracted-text`。数据库事务必须只读，输出不得放入公开 Skill 仓库。

## 2. 进入依据的最低条件

1. 正式名称、文号、发布单位和发布日期已核验；原文没有文号时明确为空，不编造。
2. 官方来源可访问或保存了带哈希的官方原件。
3. 有效状态、地域、对象和项目类型适用性明确。
4. 规划期已届满的文件默认标记为历史背景，不自动列入现行依据。
5. 用户确认核心政策的选用和排序后，才能冻结正式依据。
6. 政策核验包必须保存项目编号和匹配运行ID；回写时只允许作用于该项目最新一次已完成且输入签名一致的匹配运行，旧核验包不得覆盖新结果。

## 3. 项目事实与建设内容画像

政策召回前只读取 `confirmed` 或 `material_explicit` 的项目事实。智慧医院画像正式交付至少需要：

- `jurisdiction.province`、`jurisdiction.prefecture`；
- `organization.institution_type`、`organization.ownership`；
- `project.report_type`、`investment.regime`。

医院等级、资金来源、电子病历和互联互通目标属于可选适配事实。缺少必需事实时生成明确缺口，不得从项目名称、外地报告或常识补齐。全国性项目可免省、市两级事实和背景层级。

项目建设内容只从 `status='confirmed'` 的本期 `project_scope_item` 形成受控主题，例如电子病历、互联互通、互联网医院、远程医疗、医学影像、数据治理、患者服务、智慧管理、安全、人工智能和基础设施。待确认、分析用、拒绝或不适用范围不得触发专项政策和固定标准。每个主题保留来源 `scope_id`；主题只用于检索和适用性判断，不得把建设清单改写成政策事实，也不得反向扩大建设范围。机器规则以 `assets/knowledge-base/seeds/smart_hospital_basis_profile_v1.json` 为准。

目录候选运行的输入签名必须覆盖项目类型、规范化属地、确认事实、确认范围、受控主题、画像版本、项目锁定目录及目录内容哈希；正式条款匹配运行还必须覆盖正式 `policy_document` / `policy_clause` 语料。任一输入变化都生成新run或重新匹配，不得继续复用旧run。材料构建阶段仍须按当前属地、主题和用途许可二次复核，陈旧候选或陈旧正式匹配一律排除并形成交付阻断。

## 4. 四类归组与确定性排序

生成顺序固定为：政策类依据、行业标准依据、安全类标准依据、投资估算编制依据。文件类型由正式属性、条款主题及受控分类规则共同确定，不能仅因标题中出现“规范”“标准”等词随意改类。安全和投资规则优先于一般行业标准规则，避免把网络安全法规、成本度量规范误归为普通行业标准。

政策组：

1. 10 法律、行政法规及高位约束文件；
2. 20 国家战略和国家级规划；
3. 30 公立医院改革与高质量发展政策；
4. 31 “互联网+医疗健康”、数字健康和便民服务政策；
5. 32 国家卫生健康信息化专项政策；
6. 40 医疗信息化建设规范、评价规则和主管部门技术指引；
7. 50 省级综合及卫生健康专项政策；
8. 60 地市、区县直接相关政策；
9. 70 项目任务、批复和直接上位项目材料。

标准组从110开始，依次为强制性国家标准、推荐性国家标准、行业规范、地方标准、评价指南。安全类再按法律法规、主管部门办法、等级保护、数据与个人信息、密码应用、运维应急排序；投资类按可研编制、政府投资、成本度量、绩效评价和建设成本排序。

同组排序键固定为：

`分组顺序 → 行政层级 → 发布机关层级 → 发布日期升序 → 文号 → 标题`

人工调整必须保存理由，不得由模型临时换序。

用户在政策核验包中执行“确认、排除、调整顺序或暂缓”后，用 `extract_confirmation_decisions.mjs --kind policy` 提取决定，再用 `apply_policy_confirmations.py` 追加确认记录。排除必须填写理由；调整顺序必须填写正整数且不得重复；不满足现行有效、已核验和官方原文条件的政策即使被选择，也不得进入正式依据。回写后用 `export_policy_selection_data.py` 从同一匹配运行重新生成JSON和Markdown，再重建Excel，禁止继续使用回写前的旧矩阵。

## 5. 数量与防凑数规则

智慧医院基准画像当前使用以下“最低/目标/最高”数量：

| 分组 | 最低 | 目标 | 最高 |
|---|---:|---:|---:|
| 政策类依据 | 16 | 20 | 28 |
| 行业标准依据 | 20 | 24 | 32 |
| 安全类标准依据 | 16 | 18 | 24 |
| 投资估算编制依据 | 5 | 7 | 12 |

最低值是正式交付硬门禁，以唯一正式文件为计数单元：文号优先、官方URL次之、规范标题兜底去重。不得用重复标题、同一文件的多个条款、复制的 `policy_id`、草案、已废止文件、规划期已结束文件或与项目主题不符的条目凑数。候选超过最高值时先按重要性、适用地域、建设主题、效力和确定性排序裁剪；正式条目超过最高值转人工复核，避免清单堆砌。数量规则调整必须更新画像版本并回归，不得在提示词中临时改变。

智慧医院固定基准组由该画像保存：行业标准29项、安全21项、投资7项。它用于保证候选召回覆盖面，不是预先核验结论；每项仍须在正式库建立 `policy_document` 和 `policy_clause`、核验现行状态及官方来源，并经项目确认后才能进入正式清单。

## 6. 编制依据与政策背景

- 两处共用一份 `project_policy_match`。
- 政策背景只能使用“政策类依据”，是其精确同序子序列；行业、安全和投资类依据不得混入。
- 每段绑定一个或多个 `clause_id`。
- 先审慎概括条款，再说明它与本项目目标、范围或建设内容的关系。
- 不把“鼓励、支持、探索、供参考”改写成“必须、应当、强制”。
- 评价标准用于支撑验收目标时，必须说明评价对象和适用边界，不能提前写成“通过验收”。
- 安全法规和技术标准可在专业章节引用，不必全部堆入政策背景。

地方项目按“国家政策背景—省/自治区政策背景—市/项目建设地区政策背景”分层，正式正文最低/目标/最高分别为国家8/12/16、省级2/3/5、市级1/2/4；全国性项目只校验国家层级。没有已核验条款时只列 `【待核验】` 候选和缺口，不生成政策含义、项目响应或政策背景套话。

使用 `build_policy_section_material.py` 从同一次项目政策匹配运行生成四类编制依据和三级政策背景素材。正式模式只允许使用已确认、现行有效、已核验且带官方来源的条款，条款必须明确许可进入对应章节，政策背景摘要不能为空且不得包含超出原文约束力的禁用主张；工作模式可保留明确标记的 `【待核验】` 候选。材料签名必须覆盖匹配run、事实/范围绑定、实际正式分组、背景链、交付资格、阻断项以及重复文件、用途越界、空摘要、禁用主张和陈旧匹配诊断；签名相同而 `delivery_eligible=false` 仍不得交付。正文不得输出内部主题标签、数据库ID、核验过程提示或模板残留。

可研交付必须同时存在 `1.2.1 可行性研究报告编制依据` 和 `2.1.1 政策背景`，删除、改为不适用或只保留其中一章都不得绕过政策门禁。`1.2.1` 的四组表格行和可见结构、`2.1.1` 的三级标题、政策次序及段落正文必须与当前材料逐项闭合；正确签名不能掩盖额外的参考条目、未绑定政策陈述、错序内容或语义伪标题。全文校验与Word授权必须实时重建当前材料，再同时检查签名新鲜度和交付资格。

每个政策背景段至少回答：政策解决什么问题；哪些已确认项目事实、目标或建设范围使其适用；对应哪些建设或管理边界；如何形成可核验的实施或验收证据。缺少项目事实或条款时删去该层解释，不得用通用行业话术补长。不得只罗列文件名称，也不得把目录摘要扩写成文件原文。

## 7. 属地适配与补库

共享库按“全国核心先行、省级分批、地市区县按项目补充”建设。每次新增政策须完成官方核验、条款切分、主题标签、有效状态和项目选择快照后才能发布为共享记录。

行业、安全和投资依据可在全国固定基准上补充项目所在地的现行政策或地方标准，用于体现适配性；补充项必须与本项目建设类型直接相关、保留属地事实绑定并服从各组最高值。本项属于增强规则，库内无合格条目时保留缺口，不跨地区借用，也不自行生成。

建议服务器流程：`import_policy_catalog_postgres.py` 导入并发布 `medical_report_kb.policy_catalog_entry` 候选目录 → `sync_postgres_knowledge_snapshot.py --catalog-id ...` 把候选目录同步到项目 SQLite → 人工或受控流程补齐官方原文 → `import_verified_policies_postgres.py` 发布正式政策文件和条款 → 按项目主题再次同步正式条款。目录条目必须保存规范化 `jurisdiction_level`、`jurisdiction_code`、`jurisdiction_name`；国家项可安全回填，省、市、县项必须显式提供属地编码或经确认的名称，不得仅凭标题猜测。无服务器时使用 `import_policy_catalog_sqlite.py` 和 `match_policy_catalog_candidates.py` 完成同样的候选发现闭环。不得直接把目录项批量复制为正式 `policy_document`。
