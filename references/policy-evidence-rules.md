# 政策证据、排序和背景写作规则

## 1. 证据链

执行：`部门目录/项目线索 → 项目画像 → 官方检索 → 原文核验 → 条款提取 → 适用性匹配 → 用户确认 → 排序 → 编制依据 → 政策背景`。

搜索摘要、自媒体转载、聚合网站和模型记忆只能用于发现候选，不能作为最终政策证据。最终证据必须是官方网页、官方PDF、正式数据库或用户提供的正式原文，并保存URL、核验日期和必要原文。

部门整理的政策目录存入共享库 `policy_catalog` / `policy_catalog_entry`。目录项可以包含政策、标准、评价指南或项目文件，但它本身只是一份候选清单；只有建立对应 `policy_document`、完成官方核验、切分 `policy_clause` 并发布后，才能进入项目政策快照和报告依据。

部门目录的原始索引号不是数据库唯一键。索引号重复时必须保留全部来源行，记录出现次序并标记 `index_conflict`；不得静默覆盖、合并或丢弃。候选匹配按来源行稳定排序，标题级候选统一标记为 `structure_only` 和 `candidate_only`。

## 2. 进入依据的最低条件

1. 正式名称、文号、发布单位和发布日期已核验；原文没有文号时明确为空，不编造。
2. 官方来源可访问或保存了带哈希的官方原件。
3. 有效状态、地域、对象和项目类型适用性明确。
4. 规划期已届满的文件默认标记为历史背景，不自动列入现行依据。
5. 用户确认核心政策的选用和排序后，才能冻结正式依据。
6. 政策核验包必须保存项目编号和匹配运行ID；回写时只允许作用于该项目最新一次已完成匹配运行，旧核验包不得覆盖新结果。

## 3. 确定性排序

政策与标准分组排序，不混在一个无规则列表中。文件类型由正式文件属性确定，不能仅因标题中出现“规范”“标准”等词而随意改类。

政策组：

1. 10 法律、行政法规及高位约束文件；
2. 20 国家战略和国家级规划；
3. 30 公立医院改革与高质量发展政策；
4. 31 “互联网+医疗健康”、数字健康和便民服务政策；
5. 32 国家卫生健康信息化专项政策；
6. 40 医疗信息化建设规范、评价规则和主管部门技术指引；
7. 50 省级综合及卫生健康专项政策；
8. 60 地市、区县直接相关政策；
9. 70 项目任务、批复和直接上位项目材料。

标准组从110开始，依次为强制性国家标准、推荐性国家标准、行业规范、地方标准、评价指南。

同组排序键固定为：

`分组顺序 → 行政层级 → 发布机关层级 → 发布日期升序 → 文号 → 标题`

人工调整必须保存理由，不得由模型临时换序。

用户在政策核验包中执行“确认、排除、调整顺序或暂缓”后，用 `extract_confirmation_decisions.mjs --kind policy` 提取决定，再用 `apply_policy_confirmations.py` 追加确认记录。排除必须填写理由；调整顺序必须填写正整数且不得重复；不满足现行有效、已核验和官方原文条件的政策即使被选择，也不得进入正式依据。回写后用 `export_policy_selection_data.py` 从同一匹配运行重新生成JSON和Markdown，再重建Excel，禁止继续使用回写前的旧矩阵。

## 4. 编制依据与政策背景

- 两处共用一份 `project_policy_match`。
- 政策背景是编制依据的子序列，不得重新排序。
- 每段绑定一个或多个 `clause_id`。
- 先审慎概括条款，再说明它与本项目目标、范围或建设内容的关系。
- 不把“鼓励、支持、探索、供参考”改写成“必须、应当、强制”。
- 评价标准用于支撑验收目标时，必须说明评价对象和适用边界，不能提前写成“通过验收”。
- 安全法规和技术标准可在专业章节引用，不必全部堆入政策背景。

使用 `build_policy_section_material.py` 从同一次项目政策匹配运行生成编制依据表、标准规范表和段落素材。正式模式只允许使用已确认、现行有效、已核验且带官方来源的条款；工作模式可以保留明确标记的待确认候选。生成结果必须分别呈现“政策法规依据”和“标准规范依据”，不得输出内部主题标签、数据库ID或“政策要求政策要求”等模板残留。

政策段落至少回答四件事：文件解决什么问题、对本项目哪个目标或范围适用、形成什么建设/管理约束、将用什么记录或验收材料证明落实。不得只罗列文件名称，也不得把目录摘要扩写成文件原文。

## 5. 当前项目驱动补库

共享库按“全国核心先行、省级分批、地市区县按项目补充”建设。每次新增政策须完成官方核验、条款切分、主题标签、有效状态和项目选择快照后才能发布为共享记录。

建议服务器流程：`import_policy_catalog_postgres.py` 导入并发布部门目录 → `sync_postgres_knowledge_snapshot.py --catalog-id ...` 把候选目录同步到项目 SQLite → 人工或受控流程补齐官方原文 → `import_verified_policies_postgres.py` 发布正式政策文件和条款 → 按项目主题再次同步正式条款。无服务器时使用 `import_policy_catalog_sqlite.py` 和 `match_policy_catalog_candidates.py` 完成同样的候选发现闭环。不得直接把目录项批量复制为正式 `policy_document`。
