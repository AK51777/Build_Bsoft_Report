# 黄金测试矩阵与使用方式

## 一、最直白的用法

可以由用户提供具体文档或案例来跑，但分两种情况：

### 1. 一次性案例运行

用户提供Word、Excel、PDF、已有工作台或问题描述，Codex在仓库外建立临时项目运行并给出结果。适合定位当前问题，不需要把材料放进Git。

这只是“案例验证”，不是黄金测试，因为下次运行时没有固定的正确答案可比较。

### 2. 固化为黄金测试

当某类案例预计反复使用时，再执行：

1. 用户提供一套代表性材料，可直接提供真实案例，但必须允许脱敏测试使用。
2. Codex在仓库外登记来源、提取结构并完成脱敏；真实项目名、金额、联系人和敏感事实不得入库。
3. 用户确认该案例的正确事实、建设范围、建设方式、应阻断事项和期望输出。
4. Codex把脱敏输入、`expected-results.json`、禁止词表和自动测试写入`tests/golden_projects/<case-id>/`。
5. 记录版本和SHA-256并冻结。以后修改Skill直接运行，不需要用户再次提供原始材料。

因此，黄金测试的最小定义是：`固定输入 + 已确认正确答案 + 自动比较规则`。只有文档、没有期望结果，只能算样例。

## 二、建议的五类案例

| ID | 类型 | 用户可提供什么 | 需要确认的正确答案 | 核心断言 |
|---|---|---|---|---|
| G01 | 简单医院、标准全量新建 | 一套范围和资料较完整的医院项目 | 正式范围、目标、关键事实和标准章节结果 | 范围承载100%；数字有来源；全量新建属性不漂移 |
| G02 | 部分新建、部分升级利旧 | 含新建、升级、利旧、替换或迁移的清单及正文 | 每个系统正确建设方式和投资归属 | 建设方式混淆为0；投资不重复；旧系统与新系统不混写 |
| G03 | 缺参数、缺报价、缺背景 | 一套故意缺关键资料的案例，或从案例中脱敏删去关键字段 | 哪些内容必须待补充、哪些阶段应阻断 | AI自行补数为0；缺失披露100%；不得伪造正式完成 |
| G04 | 医共体 | 牵头医院、成员单位、共享与本地建设边界材料 | 主体、范围、投资归属和差异化章节 | 不套用单体医院结论；成员边界可追溯；共享建设不重复 |
| G05 | 删除项与参考污染 | 旧稿含已删除系统、最终清单已删除，另有参考项目材料 | 删除项、禁止继承词和冲突处置方式 | 删除项回流为0；其他项目残留为0；业务冲突输出B类卡 |

不要求用户一次提供五套。优先从最常出问题、最有代表性的一套开始，建立G01或G02，再逐步补齐。

## 三、相似案例与知识库判断

相似案例判断可以由黄金案例验证，但不能只比较标题或医院名称。先硬过滤权限、发布状态、文种、项目类型和知识版本，再比较范围覆盖、建设方式、验收目标、地域政策、证据完整度和禁止继承项。

输出只允许：

- `复用`：复用结构和受审通用语料，项目事实仍重新绑定；
- `组装`：多个案例或知识块分别覆盖部分章节；
- `重建`：没有合格候选或关键边界冲突。

阈值写入fixture或项目配置，不在Prompt中临时决定。多候选或业务边界变化必须由用户确认。

## 四、文件契约

建议结构：

```text
tests/golden_projects/Gxx-short-name/
├── input-manifest.json
├── project-config.json
├── inputs/                    # 仅合成或脱敏材料
├── expected-results.json
├── forbidden-terms.txt
└── test_case.py
```

`expected-results.json`至少记录：预期事实状态、范围ID与建设方式、允许/禁止的章节内容、预期门禁、预期决策类型和必须为零的污染项。

## 五、最小回归选择

- 字段、参数、schema或日志：相关单元测试 + 1个最接近案例。
- 范围建设方式：G02；缺参和防编造：G03；医共体：G04；删除项和污染：G05。
- 全量生成主链或发布：G01～G05全部运行；涉及Word时再执行Word冒烟和全页渲染。
