# 事实核验与用户确认规则

## 1. 信息类型

| 类型 | 处理 |
|---|---|
| 明示项目事实 | 绑定来源和证据位置后按状态使用 |
| 可计算事实 | 保存公式和前提ID，复核后使用 |
| 政策/标准事实 | 绑定已核验官方条款 |
| 技术默认或行业惯例 | 只写为 `【分析建议】`，不得冒充现状 |
| 上下文推断或项目假设 | 进入推断台账，按重要性决定是否必须确认 |

## 2. 重要性

- A 阻断：正式名称、建设单位、范围、总投资、资金来源、周期、核心验收目标和部署边界。
- B 重要：现有系统、厂商、迁移范围、接口、容量、数量和关键技术条件。
- C 建议：技术路线、实施优化和行业惯例，只能使用审慎语气。
- D 通用：稳定定义和通用说明，不能推出项目专属结论。

## 3. 核验流程

1. 登记来源并计算哈希。
2. 把复合句拆成可以独立判断真假的原子事实。
3. 为事实登记单位、统计时点、证据位置、重要性和确认要求。
4. 同一口径不同值进入冲突组，不按来源优先级静默选择。
5. 把技术默认和上下文判断移入推断台账。
6. 执行规则检查后生成 `事实核验包.xlsx`。
7. 单轮只保留最多15项会改变边界、投资、技术、合规或结论的问题。
8. 用户填写核验包后，用 `extract_confirmation_decisions.mjs --kind fact` 提取决定；提取时校验工作表名称、表头、决定值、修改口径、建议标准值、单位、时点、确认人和确认时间。
9. 用 `apply_project_confirmations.py` 校验项目编号和事实基线版本，把决定写入追加式 `confirmation_record`，再更新事实、结构化值、单位、时点、推断和问题状态；同一决定重复导入不得产生重复记录。仍含占位语义的待补或冲突事实不得通过“确认”直接转为已确认，必须以“修改”提供非占位值。占位识别至少覆盖“待补充、待确认、待定、暂缺、暂无、未知、不详、TBD、TBC、N/A”等变体；填写统计时点时统一使用 `YYYY-MM-DD`。
10. 对用户“确认”或“修改”后的事实，保留原证据，同时把本次用户确认新增为A级证据并关联事实；不得用新证据覆盖或删除修改前证据。
10. 只有A/B级事实和必须确认的推断全部解决后，才允许使用 `--freeze` 冻结事实基线；变更后列出受影响的政策、章节、清单、投资和指标。

## 4. 门禁

- A/B级 `待确认`、`待补充` 或 `冲突` 不得作为确定性正文事实。
- `材料明确` 代表材料原文明确，不代表院方已确认最终决策。
- 用户口头或对话确认可以形成 `已确认`，但必须记录确认日期和口径。
- 推断置信度再高也不能替代项目事实确认。
- 可继续编写不依赖缺失事实的段落，但必须保留占位和影响说明。

## 5. 隐性知识补充

发现常见但材料未写明的条件时，按下列顺序处理：

1. 判断它是通用定义、技术默认还是项目特定假设；
2. 通用定义核验权威来源后只用于解释；
3. 技术默认进入 `inference_record`，使用 `通常、可考虑、建议` 等条件语气；
4. 会影响范围、投资、接口、部署或验收的隐性条件必须转为确认问题；
5. 不重要且不影响结论的隐性条件可以不问，但不得写成项目现状。
